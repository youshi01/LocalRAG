# 模型辅助知识库检索设计

## 背景

LocalRAG 当前主要依赖原始问题、可选的查询改写和关键词/向量召回。对“请总结全部内容”“如果基于当前资料实现，下一步是什么”这类需要先判断资料范围、再组织多个检索意图的问题，单一关键词容易只命中摘要，导致回答误判为“资料不足”。

## 目标

1. 由聊天模型输出结构化的检索计划，而不是暴露或保存模型思维链。
2. 计划至少包含是否需要知识库、检索意图、检索查询和回答模式。
3. 知识库检索始终保留用户原问题，并合并模型生成的查询；支持向量、关键词、混合和结构化检索的现有路径。
4. 首轮证据不足时最多补检索一轮，补检索只能追加证据，不能绕过现有知识库范围、索引围栏和证据门控。
5. 模型规划失败、超时、JSON 非法或返回空查询时，完全回退到现有确定性检索，不阻断聊天。
6. 最终回答继续只允许基于证据；资料明确事实与“基于资料推导”的建议分开，不补造资料之外的产品、接口、负责人、时间和效果。

## 非目标

- 不实现通用 Agent、工具调用循环或无限检索。
- 不把文档正文直接当作系统指令执行。
- 不替换现有 Qdrant、结构化表格查询、关键词融合、重排和引用支持度校验。
- 不记录完整思维链；只记录有限的检索计划元数据和轮次统计。

## 设计

### 1. 规划器接口

新增 `RetrievalPlanner` 接口和 `LLMRetrievalPlanner` 实现。输入包括用户问题、最近对话、知识库/文档范围、当前轮次、上一轮查询和有限的证据摘要；输出固定 JSON：

```json
{
  "needKnowledge": true,
  "intent": "implementation_advice",
  "scope": "current_knowledge_base",
  "queries": [
    "当前资料中的系统、风险和已有建设内容",
    "文档中的实施约束、排查建议和处置流程"
  ],
  "answerMode": "grounded_inference"
}
```

模型输出只作为检索建议。服务端会重新清洗、去重、限量，并强制保留原始问题；`needKnowledge=false` 只表示本轮不需要调用知识库，不改变聊天模型的普通回答能力。

### 2. 检索流程

```text
结构化表格确定性查询
  └─ 命中：直接返回结构化证据
  └─ 未命中：模型规划器（可关闭）
      └─ 规划失败：现有原问题/查询改写路径
      └─ 需要知识库：原问题 + 规划查询 → 现有检索
          └─ 证据低置信/为空：最多再规划一次 → 合并证据 → 现有选择策略和证据门控
```

补检索不会超过配置的最大轮数，默认 2。每轮有独立超时，整体仍受请求上下文约束。补检索的证据摘要只包含截断后的文本片段、数量和信号，不包含系统提示或可执行指令。

### 3. 配置

后端 `RetrievalConfig` 增加：

- `enableModelRetrievalPlanner`
- `modelRetrievalMaxRounds`

`ServerConfig` 增加环境变量配置：

- `ENABLE_MODEL_RETRIEVAL_PLANNER`
- `RETRIEVAL_PLANNER_MAX_ROUNDS`
- `RETRIEVAL_PLANNER_TIMEOUT_SECONDS`

前端检索设置增加“模型辅助检索”开关和说明，旧配置缺少字段时使用安全默认值；保存后沿用现有配置接口。

### 4. 健壮性和安全

- 规划器只能调用当前已配置的聊天模型，使用受限超时和低温度。
- 严格解析 JSON；代码围栏可被剥离，但非法 JSON、空 `queries`、过多查询均视为规划失败并回退。
- 所有查询强制限制长度和数量，防止模型输出导致高成本检索。
- 检索范围始终由服务端的 `KnowledgeBaseID`、`DocumentID` 和索引围栏决定，模型不能扩大范围。
- 日志仅记录状态、轮次、查询数量和错误类型，不记录 API Key 或完整用户内容。

## 验收标准

- 单元测试证明合法计划能解析、非法计划能失败并回退、`needKnowledge=false` 不触发召回。
- 检索测试证明模型查询和原问题都会被使用，规划失败回到旧路径，证据不足最多补一轮。
- 现有后端测试全部通过；前端类型检查、Lint 和测试全部通过。
- `git diff --check` 通过，并在最终报告中明确真实服务/Docker 是否实际验证。
